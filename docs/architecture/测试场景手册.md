# 测试场景手册（Web 运行时冒烟 + 单元/评估回归）

> 本手册覆盖三类测试，按「成本递增、置信度递增」排序。前两层可在离线完成，第三层需调用真实 LLM。
> 单元测试已覆盖纯函数逻辑（83 passed），**本手册重点在 LLM 运行时行为验证**——这是单元测试的盲区。

---

## 第 0 层：基建验证（离线，~1 分钟）

确认环境干净、测试可独立运行。

```bash
# 在项目根目录执行

# 0.1 全量单元测试（零参数即可，pyproject.toml 已锁定 testpaths=tests）
python -m pytest
# 预期：83 passed

# 0.2 任意单文件可独立运行（验证循环 import 已根治）
python -m pytest tests/test_kv_header_strip.py -v
# 预期：6 passed（修复前单独跑此文件会 ImportError）
```

**判读**：
- `83 passed` → 基建正常
- 若出现 `ImportError ... circular import` → 回归到 `agent/core/__init__.py` 的 `__getattr__` 延迟加载被破坏，检查是否有人重新加了顶层 `from agent.core.team import`
- 若 `collected 0 items / N errors` 且报错指向 `agno_repo/` → `pyproject.toml` 的 `testpaths` 配置丢失，或 pytest 没读到 `pyproject.toml`（确认在项目根目录执行）

## 第 2 层：Web 界面冒烟测试（需启动 Chainlit，手动操作）

**这是当前最大的测试缺口**——单元测试全是纯函数/打桩，step_planner、multi-step-plan skill、#14 修复都依赖真实 LLM 运行时行为，从未在 Web 端验证过。

### 启动

```bash
chainlit run web/chainlit_app.py
# 浏览器自动打开 http://localhost:8000
```

前置：`.env` 已配置 `SILICONFLOW_API_KEY`（当前已就位）。

---

### 场景 1：单一意图不误触发（回归保护）✅ 最重要

**目的**：验证复合意图分解不会误伤单一意图。这是 7.6 段逻辑（`user_message_handlers.py:222`）的核心风险。

| 步骤 | 操作 | 预期结果 | ❌ 失败征兆 |
|------|------|---------|------------|
| 1 | 上传任意日志 Excel（或粘贴几行日志） | 文件被读取，session 有 raw_data | — |
| 2 | 输入：`字段映射` | 直接走 mapping 流程，返回映射表 | 出现 `[PLAN:...]` 标记（误触发分解）|
| 3 | 输入：`提取枚举值` | 直接走 enum 提取 | 被分解成多步 |
| 4 | 输入：`威胁类型映射` | 直接走 threat | 被分解成多步 |

**判读要点**：单一意图命令**绝不应**出现 `[PLAN:...]`。RouterAgent 应直接路由到对应专家 Agent。

---

### 场景 2：复合意图自动分解（批5 核心功能）⭐ 关键

**目的**：验证 multi-step-plan skill 端到端链路：RouterAgent 识别复合意图 → 输出 `[PLAN:...]` → step_planner 解析 → 逐步自动执行。

| 步骤 | 操作 | 预期结果 | ❌ 失败征兆 |
|------|------|---------|------------|
| 1 | 上传日志 Excel（含 alarm_name 等字段） | 文件被读取 | — |
| 2 | 输入：`先提取 alarm_name 的枚举值，然后做威胁类型映射` | ① 看到 RouterAgent 的分解说明（如"我将先执行枚举提取，再做威胁映射"）<br>② 说明文字中**不含** `[PLAN:...]` 原始标记（应被清理）<br>③ 自动开始第一步 | ① 标记 `[PLAN:enum\|threat]` 直接显示给用户（清理逻辑失败）<br>② 无后续自动执行 |
| 3 | 观察执行 | 第一步（enum）自动执行 → 完成后第二步（threat）自动执行 | 只执行第一步就停 |
| 4 | 观察队列 | 两步都完成后，无残留 loading 消息 | 卡在"⏳ 自动执行步骤..." |

**进阶变体**（验证不同步骤组合）：
- `把这些枚举值做威胁映射然后填充回子规则里` → 期望 `[PLAN:threat|fill]`
- `先做字段映射，然后提取 severity 字段的枚举值` → 期望 `[PLAN:mapping|enum]`

**日志排查**：查看 `agent/logs/app_*.log`，搜索 `[PLAN]` 和 `[STEP]` 关键字：
```
[PLAN] RouterAgent 分解复合意图为 2 步: ['enum', 'threat']
[STEP] 执行步骤: enum（原文: ...）
[STEP] 步骤 enum 完成，剩余 1 步
[STEP] 执行步骤: threat（原文: ...）
```

### 场景 3：#14 回归验证（KV 日志头剥离）

**目的**：验证 `header_end_marker == 字段分隔符`时不再丢字段。

| 步骤 | 操作 | 预期结果 | ❌ 失败征兆 |
|------|------|---------|------------|
| 1 | 上传含 `skyeye_ioc` 类型日志的 `SearchResult-*.xlsx`（tab 分隔 KV 格式） | 文件被读取 | — |
| 2 | 输入：`日志类型提取` | 解析结果中 `type` 字段 **matched > 0**（如"远控木马"被正确归类） | `type` 字段 matched=0（回归到 rpartition bug，只剩 attck_tech） |
| 3 | 检查完整解析 | 多个字段（access_time/tid/type/rule_desc/...）都被提取 | 只有最后一个字段 attck_tech |

**判读要点**：`type` 字段必须能匹配上。修复前 `rpartition('\t')` 会把 body 切到只剩最后一个字段 `attck_tech`，导致 `type` 丢失、matched=0。

| 步骤 | 操作 | 预期结果 |

## 第 3 层：LLM 准确率评估（需 API 调用，~5-15 分钟/脚本）

`eval/` 目录下的脚本会真实调用 LLM，评估生产准确率。这些是单元测试无法覆盖的端到端质量门禁。

> 注意：`eval/` 在 `.gitignore` 中被忽略（运行时生成报告），但脚本本身已存在于本地。

| 脚本 | 评估内容 | 运行命令 | 关注指标 |
|------|---------|---------|---------|
| `test_llm_accuracy.py` | LLM 字段映射 Precision@1 + 负例判断 | `pytest eval/test_llm_accuracy.py -v -s` | Precision@1、负例准确率 |
| `test_candidate_recall.py` | 向量召回 top-K 覆盖率 | `pytest eval/test_candidate_recall.py -v -s` | Recall@K |
| `test_skills_e2e.py` | Skills 端到端（连续操作链） | `python -m eval.test_skills_e2e` | 各步骤成功率 |
| `test_full_mapping_cli.py` | 全量映射 CLI 集成 | `python -m eval.test_full_mapping_cli` | 端到端映射准确率 |

**运行前确认**：
```bash
# 确认 .env 中 API key 已配置
python -c "from dotenv import load_dotenv; import os; load_dotenv(); print('SF key:', '✓' if os.getenv('SILICONFLOW_API_KEY') else '✗ 缺失')"
```

**报告位置**：`eval/reports/`（运行后自动生成）。

## 测试矩阵速查

```
离线（CI 可跑）
├── 第0层  python -m pytest                    → 83 passed（基建）
└── 第1层  python -m pytest tests/test_xxx.py  → 模块级回归

需 LLM（手动/定时）
├── 第2层  chainlit run web/chainlit_app.py    → Web 冒烟（场景1-5）
└── 第3层  pytest eval/...                     → 准确率评估
```

## 已知限制

1. **第 2 层无法自动化**：Chainlit 消息流依赖运行时，当前无 headless 测试框架。若需自动化，可考虑用 `pytest-asyncio` + mock `cl.Message` 模拟消息流（参考 `test_step_planner.py` 的打桩模式扩展）。
2. **LLM 结果非确定性**：场景 2/3 的 LLM 输出每次可能不同，判读以"结构是否正确"（有无标记、字段是否提取到）为准，而非字面值。
3. **`agno_repo/` 已加入 `.gitignore`**：本地保留不影响测试（`pyproject.toml` 已用 `testpaths` + `norecursedirs` 双重隔离）。
