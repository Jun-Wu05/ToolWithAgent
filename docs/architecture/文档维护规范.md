# 文档维护规范

> **适用范围**：本项目的所有 Markdown 文档（`docs/`、`README.md`、`CHANGELOG.md`）
> **最后更新**：2026-05-14

---

## 1. 文档分类

| 类型 | 存放位置 | 受众 | 更新频率 |
|------|----------|------|----------|
| **入口文档** | 根目录 `README.md` | 所有开发者/用户 | 每次大版本发布 |
| **变更日志** | 根目录 `CHANGELOG.md` | 开发者 | 每个合并请求后 |
| **架构文档** | `docs/architecture/` | 开发者/架构师 | 重大架构变更时 |
| **方案设计** | `docs/`（如 `日志特征提取方案_*.md`） | 开发者 | 方案评审/实施后 |
| **项目概要** | `docs/项目概要_*.md` | 通用 | 阶段性总结 |
| **上下文摘要** | `context_summary/` | AI Agent | 每次关键任务完成时 |
| **代码内注释** | 源码文件 | 开发者 | 随代码变更持续 |

## 2. 文件命名规范

### 2.1 带时间戳的文档

```
格式：YYYYMMDD[_HHMM]_主题.md
示例：20260514_架构概览.md
     20260513_1010_日志特征提取方案.md

规则：
- 时间戳在前，主题在后，用下划线分隔
- 仅日期：YYYYMMDD（8位），用于不需要精确时间的归档文档
- 日期+时间：YYYYMMDD_HHMM（12位），用于可能有多个同主题版本的文档
```

### 2.2 不带时间戳的文档

```
README.md          — 必须大写，GitHub 约定
CHANGELOG.md       — 必须大写，社区约定
文档维护规范.md    — 没有版本概念的固定标准
```

## 3. 文档内容规范

### 3.1 必须包含的元数据头

```markdown
# 文档标题

> **文档版本**：YYYY-MM-DD
> **对应分支**：branch-name（可选）
> **最新提交**：commit-hash（可选）
```

### 3.2 代码块的格式要求

- 所有代码块必须指定语言标识符（```python, ```bash, ```json 等）
- 伪代码/流程图用 ASCII 艺术图或 Mermaid
- 大于 30 行的代码块应考虑拆分或精简

### 3.3 表格规范

- 表格必须包含表头分隔线（Markdown 标准格式）
- 列数 > 5 的表格考虑拆分成多表或列表形式

### 3.4 链接规范

- 内部文档链接使用相对路径（`docs/architecture/架构概览_20260514.md`）
- 外部链接使用完整 URL
- 避免裸链接（`<https://...>`）

## 4. 文档生命周期

### 4.1 新建文档

1. 确定文档类型和命名方式（见第 2 节）
2. 确定存放目录（见第 1 节）
3. 添加元数据头（见第 3.1 节）
4. 更新 `README.md` 中的"文档导航"表格

### 4.2 更新文档

1. 小修正（错别字、格式）：直接提交，不更新文档版本号
2. 内容更新（新增章节、修改关键信息）：更新文档版本号和日期
3. 重大重写：新建带新时间戳的文件，旧文件可在确认无用后删除

### 4.3 删除/废弃文档

1. 确认该文档无其他文档引用
2. Git 删除 + commit 说明中注明原因
3. 更新 `README.md` 中的"文档导航"表格

## 5. CHANGELOG.md 维护规则

遵循 [Keep a Changelog](https://keepachangelog.com/) 格式：

- **版本号规则**：Bug 修复递增（`v0.0.x` → `v0.0.x+1`）
- **分类**：`Added` / `Changed` / `Fixed` / `Deprecated` / `Removed`
- **优先级**：Added → Changed → Fixed → Deprecated → Removed
- **每个条目**：一个 Git 提交对应一行简洁描述（不包含 commit hash）

## 6. 上下文摘要 (context_summary/) 规范

上下文摘要是 AI Agent 使用的项目状态摘要，用于跨会话保持上下文。

### 6.1 格式要求

```markdown
# context_summary_YYYYMMDD_HHMM_主题简述

## 1. 核心目标
[1-2 句话说明本次任务的最终目标]

## 2. 已完成的关键代码/决策
- **文件路径**（精确到行号）：变更说明
- 引用关键代码片段（≤10 行）

## 3. 当前卡点 / 未解决问题
- 问题描述 + 技术原因 + 影响范围

## 4. 下一步任务
1. 具体操作步骤
2. 验证标准
3. 预期结果
```

### 6.2 命名规则

`context_summary/context_summary_YYYYMMDD_HHMM_主题简述.md`

## 7. 质量检查清单

在提交文档变更前，检查以下项目：

- [ ] 文件名符合命名规范
- [ ] 包含元数据头（版本、日期、分支）
- [ ] 所有代码块指定了语言
- [ ] 所有内部链接可访问
- [ ] 表格格式正确
- [ ] 无拼写错误
- [ ] 已在 README.md "文档导航"中注册（如果是新文档）
- [ ] 如果是 CHANGELOG 变更，格式符合 Keep a Changelog

## 8. 禁止事项

- ❌ 文档内容与代码实际行为不一致
- ❌ 复制粘贴大段代码而不做解释
- ❌ 在文档中硬编码 API 密钥、密码、Token
- ❌ 在技术文档中使用模糊用语（"可能"、"也许"、"差不多"）
- ❌ 文档命名包含特殊字符（空格、括号、引号）——统一使用下划线
