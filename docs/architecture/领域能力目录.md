## 1. 目的与使用方式

本文按领域能力而不是偶然的目录位置导航生产代码。维护者和 Agent 应先从能力索引找到模块接口、依赖方向和测试接缝，再进入实现文件。

本目录是版本化架构文档，不是运行时服务定位器，也不是全局注册中心。生产代码不得读取本文完成模块发现、依赖注入或动态注册；真实运行时组合仍由 Application 运行时及其适配器拥有。

## 2. 记录 schema

每项能力必须维护以下字段。一个能力可以跨越多个物理文件，但只能呈现一个对调用者有意义的接口说明。

| 字段 | 必填 | 含义 | 更新触发器 |
|---|---|---|---|
| 能力名称 | 是 | 使用 `CONTEXT.md` 领域语言命名 | 领域概念或模块职责改变 |
| 职责 | 是 | 模块隐藏的实现复杂性以及向调用者提供的杠杆 | 接口不变量或错误模式改变 |
| 领域术语 | 是 | 该能力使用的权威业务词汇 | `CONTEXT.md` 术语调整 |
| 公共入口 | 是 | 调用者实际依赖的函数、类型、门面或类型化步骤 | 入口新增、迁移或废弃 |
| 上游 | 是 | 谁调用该能力 | 生产组合关系改变 |
| 下游 | 是 | 该能力依赖的领域事实、策略或外部集成 | 依赖方向改变 |
| 测试接缝 | 是 | 保护接口与可观察行为的最高层回归位置 | 接口或测试策略改变 |
| 生命周期状态 | 是 | `planned`、`active`、`active-characterization-needed` 或 `legacy-audit-needs-info` | 迁移或审计结论改变 |
| 负责人类别 | 是 | Application runtime、Application adapter、Contracts、domain module、Skill、Web adapter 或 HITL | 所有权改变 |
| 模块角色 | 是 | 本文定义的五种接口用途，可多选 | 接口用途改变 |
| 物理所有者 | 是 | 当前承担实现的包、类型或门面 | 生产代码迁移 |
| 静态分析盲区 | 是 | 延迟导入、重导出、动态加载、框架注册或仓库外依赖 | 调用方式改变 |
| 深度审查 | 是 | 职责深度、杠杆、局部性和删除测试结论 | 模块接近软性预算或准备拆分 |

## 3. 模块角色分类

模块角色描述接口在系统中的用途，不等同于物理目录：

- **public entrypoint**：其他模块应优先依赖的稳定入口或门面。
- **domain transformation**：执行映射、填充、分类、解析规则或字段调整等确定性领域变换。
- **policy**：选择策略、校验不变量、计算覆盖率或决定重试等规则。
- **integration adapter**：在接缝处把类型化步骤或外部框架转换为内部接口。
- **legacy/audit candidate**：仓库内疑似无调用、重复所有权或待确认外部依赖的模块；该分类不授权删除。

对模块应用删除测试：若删除后复杂性会在多个调用者中重新出现，该模块具有深度，应保留或深化；若复杂性直接消失，才进入五证据删除审计。物理行数不是删除测试。

## 5. 能力详情

### 5.1 请求规划与类型化执行

- **职责**：把自然语言或确定性 Action 转换为类型化计划；执行依赖、失败关闭、结果账本和进度。
- **领域术语**：PlannerAgent、PlanExecutor、解析规则、字段映射、填充、字段调整。
- **公共入口**：`run_user_request`、`run_deterministic_plan`、`PlanExecutor.execute`、默认适配器组合。
- **上游**：Chainlit 文本、文件和 Action 适配器，以及 V2 API/Worker 的持久化业务桥。
- **下游**：Contracts、SessionFacts、Application adapters、专业 Agent 与领域能力。
- **测试接缝**：类型化计划只调用 Planner 一次；步骤依赖、失败关闭、执行报告和确定性 Action 回归。
- **生命周期状态 / 负责人类别**：`active` / Application runtime。

### 5.2 主数据与可引用会话产物

- **职责**：原子管理主数据、附件、派生配置和可引用会话产物，并投影不含敏感值的 SessionFacts；其中 `available_fields` 拥有 Planner 点名词典语义，`mappable_fields` 拥有字段映射执行池语义，上传配置另投影由非空 `normalize[].field` 判定的已映射/未映射计数。
- **领域术语**：主数据、枚举映射附件、可引用会话产物、填充。
- **公共入口**：`SessionState`、`build_session_facts` 及类型化 Artifact slots。
- **上游**：文件输入、请求运行时和 Application adapters。
- **下游**：Contracts；不依赖 Web。
- **测试接缝**：新主数据替换、附件原子合并、安全事实投影、跨轮产物引用。
- **生命周期状态 / 负责人类别**：`active` / Application runtime + Contracts。

### 5.3 StandardFieldCatalog 与候选检索

- **职责**：只读 StandardFieldCatalog 统一 schema、标准字段/同义词/tag 规则资源解析、名称/别名 lookup 与确定性索引；候选检索模块继续拥有 embedding 复合文本、缓存生命周期、模型调用、候选检索、排除和排序。
- **领域术语**：标准字段、字段映射、事件名称标注。
- **公共入口**：Catalog 入口为 `StandardFieldCatalog` 与 `get_standard_field_catalog`；检索入口仍是 `application.field_runtime` 浅层兼容门面、`init_field_cache`、`batch_retrieve_candidates` 和映射工具查询门面；另新增结构化出口 `batch_retrieve_candidates_table`（field → [(标准名, 得分, 英文名, by_stripped变体)]，#180），markdown 出口由其渲染且字节不变，冲突裁决改消费结构化表。`field_retriever`、`standard_mapper` 与 Prompt loader 均已通过既有入口消费 Catalog，旧入口继续保留；Catalog 不包含整个候选检索实现。
- **上游**：字段映射输入构建、Web 启动缓存初始化和确定性字段映射 Action。
- **下游**：标准字段、同义词和 tag 规则资源；embedding 模型与缓存文件。
- **测试接缝**：Catalog 兼容接缝——资源 schema、lookup、索引确定性、cache meta、稳定失败、现有入口、字段排除和日志脱敏。
- **模块角色 / 物理所有者**：Catalog 是 `agent/core/standard_field_catalog.py` 拥有的 domain transformation；候选检索是 policy + integration adapter，映射工具是消费门面而不是 Catalog 所有者。
- **静态分析盲区 / 深度审查**：Application 浅层门面会遮蔽真实下游；删除当前检索模块会把缓存、embedding、排除和排序复杂性分散到多个调用者，因此当前模块应在兼容迁移中深化而非直接移除。
- **生命周期状态 / 负责人类别**：Catalog 与当前候选检索均为 `active` / domain module + Application runtime。

### 5.4 字段映射与事件名称标注

- **职责**：从 SessionFacts `mappable_fields` 构建批次，执行候选检索与专业 Agent 映射，处理超时拆批、重试、漏字段补查，并在写回前确定性裁决标准字段占用冲突；纯上传配置仅处理 field 为空的 index，既有映射优先占用并保护 `field/entity/sim/core`，全已映射时零模型调用成功；系统生成的 `mapped_sub_rules` 保持全量重映射覆盖语义。
- **领域术语**：字段映射、标准字段、事件名称标注、主数据。
- **公共入口**：类型化 FieldMappingStep、`FieldMappingAdapter`、`FieldMappingBatchRunner`、`resolve_field_mapping_conflicts`。
- **上游**：PlanExecutor 与确定性字段映射 Action。
- **下游**：标准字段候选检索、专业 Agent、事件名称分类规则和 Session。
- **测试接缝**：Planner 点名词典/映射候选池隔离、批次大小、并发、超时拆批、漏字段补查、事件名称守卫、一次性 Session 写回与 Artifact，以及一对一冲突的精确命中/相似度/行序降级与既有映射占用。
- **生命周期状态 / 负责人类别**：`active` / Application adapter + domain module。

### 5.5 日志解析与日志分类策略

- **职责**：识别日志格式、定位分类特征字段、按 JSON/KV/Header 策略分类、计算 coverage、回填样本并生成日志分类产物；独立的日志知识仓储用 SQLite 统一约束三状态申请、最多 10 条去重样例、审核、原子替代与旧库迁移。正常分类不自动创建申请。
- **领域术语**：日志类型提取、分类特征字段、解析规则、入口规则、子规则。
- **公共入口**：类型化 LogParseStep 与 `LogParseAdapter` 是 integration adapter；`agent.tools` 的 headless 门面是 public entrypoint；`decide_body_key_route` 是首条独立 Pipeline policy；`LogKnowledgeRepository` 是 SQLite 仓储入口。
- **上游**：PlanExecutor 和日志解析专业 Agent。
- **下游**：格式识别、特征定位、LLM postprocess 和解析规则生成。
- **测试接缝**：Log Parser 行为接缝——调用顺序、Session、进度、稳定错误、JSON/KV/Header 选择、coverage、marker、fallback、调用次数、无自动知识副作用和历史成功结果；知识仓储另验证 schema 幂等、状态不变量、样例上限、替代回滚与删除、安全迁移；`tests/test_log_classification_policy.py` 独立保护日志体键 80% 路由边界。
- **模块角色 / 物理所有者**：日志解析步骤属于 Application adapter；JSON/KV/Header、coverage 与 fallback 属于 domain policy；日志知识仓储是 `agent/tools/log_pattern_store.py` 拥有的 domain transformation。
- **静态分析盲区 / 深度审查**：Application → `agent.tools` 门面 → Pipeline 实现形成两跳调用，函数内导入会被仅分析顶层 import 的工具遗漏。三个角色分别产生调用、策略和副作用局部性，不应合并为一个模糊条目。
- **生命周期状态 / 负责人类别**：解析步骤、首条分类策略和知识仓储均为 `active` / Application adapter + domain module。

`log_pattern_store` 生命周期是**在用能力**，不是 legacy/audit candidate。SQLite 是唯一运行时事实源，不再读写 NumPy/JSON sidecar；JSON、KV 与 Header 正常分类不导入或调用仓储。用户显式提交、候选排序、确定性回放和 UI 仍是后续切片。

### 5.6 解析规则生成

- **职责**：把日志分类和字段映射结果转换为入口规则、子规则、filter 与 normalize，并承接字段映射回写；人工选择按子规则位置与完整原始字段路径原子校验合法标准目标、平台固定字段及同一子规则占用，目标变化时清理旧值映射和默认值，保留提取样例。
- **领域术语**：解析规则、入口规则、子规则、字段映射、Draft、Artifact。
- **公共入口**：解析规则生成包门面、字段来源提取入口及 `agent.tools.rule_generator.apply_manual_field_mappings`。
- **上游**：日志分类和字段映射 Application adapters；V2 Draft 校验及 `BusinessApplication.apply_mapping_draft` 确定性桥。Draft 不作为 Planner 输入。
- **下游**：只读 StandardFieldCatalog、规则 filters、normalize、导出与 Session 派生配置；不依赖 V2 数据库或 Web。
- **测试接缝**：规则根结构、入口/子规则语义、字段来源、导出键顺序和中文编码；`tests/test_manual_field_mappings.py` 保护纯函数原子性、目录与来源约束，V2 Draft 与独立回归保护占用确认、精确联动、revision、失败回滚和产物一致性。
- **生命周期状态 / 负责人类别**：`active` / domain module。

### 5.7 枚举、威胁类型映射与填充

- **职责**：提取枚举值、生成威胁类型映射并把显式依赖或白名单可引用会话产物填充回配置。
- **领域术语**：枚举提取、威胁类型映射、填充、枚举映射附件、可引用会话产物。
- **公共入口**：Enum、Threat、Fill 类型化步骤及其 StepAdapter。
- **上游**：PlanExecutor、主数据与附件上传。
- **下游**：专业 Agent、Session Artifact slots、`normalize[].mappings`。
- **测试接缝**：显式依赖、附件按 Sheet 原子合并、目标字段消歧、填充原子性和导出产物。
- **生命周期状态 / 负责人类别**：`active` / Application adapter + domain module。

### 5.8 FieldSkillAdapter 与字段调整 Skills

- **职责**：把五类类型化字段调整步骤接到真实 Skills 脚本，执行字段寻址、规则范围、引用守卫、事件名称绑定、稳定错误映射和 Session 原子写回。
- **领域术语**：字段调整、入口规则、子规则、事件名称标注、解析规则。
- **公共入口**：`FieldSkillAdapter` 是 integration adapter；`FIELD_SKILL_REGISTRY`、字段寻址、规则范围、引用守卫和事件绑定是 policy；五类 StepSpec 是调用接口。
- **上游**：PlanExecutor 与确定性字段调整请求。
- **下游**：添加、删除、合并、Base64 解码和正则提取 Skills 脚本。
- **测试接缝**：FieldSkillAdapter 契约接缝——Step 到 Skill、字段/规则寻址、引用与事件绑定、Session 原子写回、Artifact、稳定错误和 per-entity 行为；`tests/test_field_skill_reference_policy.py` 独立保护 merger 与占位符悬空引用扫描。
- **模块角色 / 物理所有者**：Adapter 与共享 policy 由 Application adapters 拥有；五类脚本是独立的 domain transformation，由 Skills 拥有。
- **静态分析盲区 / 深度审查**：脚本经注册表和 `importlib` 动态加载，静态 caller 为零是预期；删除 Adapter 会把寻址、守卫、错误与原子写回复杂性散回五条调用路径，因此 Adapter 有深度。
- **生命周期状态 / 负责人类别**：Adapter、首条共享引用守卫策略与 Skills 均为 `active` / Application adapter + Skill。

Skills 脚本是数据变换的单一事实源；共享策略深化不得复制脚本逻辑，也不得按五类操作机械产生五个浅层 Adapter。

### 5.9 Prompt 资产与模型提供商

- **职责**：按包相对路径加载 Prompt；由 ProviderSpec 单点声明模型提供商参数，并由 Application 管理会话设置与 Team 生命周期。
- **领域术语**：模型提供商、PlannerAgent、分类特征字段、事件名称标注。
- **公共入口**：Prompt 包公开加载器、ProviderSpec 注册表、Application 模型入口。
- **上游**：Planner、专业 Agent、日志 Pipeline 和 Web 设置适配器。
- **下游**：包内 Prompt 资产、模型 SDK 与会话设置。
- **测试接缝**：非仓库工作目录加载、缺失策略、注册表完整性、设置覆盖和 Team 懒初始化。
- **生命周期状态 / 负责人类别**：`active` / domain module + Application runtime。

### 5.10 文件输入、导出与 Web 交付

- **职责**：确定性解码文件并提交主数据；把类型化产物导出为稳定 JSON/Excel/Base64；由 Web 适配输入、进度与渲染。
- **领域术语**：主数据、枚举映射附件、解析规则、字段映射、填充。
- **公共入口**：Application 文件输入、ExportAdapter、Web 文件/Action/Renderer handlers。
- **上游**：Chainlit Element、Action 与用户消息。
- **下游**：SessionState、PlanExecutor、类型化 Artifact 和下载元素。
- **测试接缝**：文件类型分流、主数据原子提交、导出根结构/字节、下载语义、Web 不反向渗入 Application。
- **生命周期状态 / 负责人类别**：`active` / Application runtime + Web adapter。

### 5.11 五证据删除审计

- **职责**：在任何删除决定前分别收集生产导入、动态注册、包级重导出、测试依赖和仓库外依赖证据。
- **领域术语**：本能力是架构治理，不新增业务术语。
- **公共入口**：独立审计 Issue、证据记录和 HITL 结论；不是 Python 运行时接口。
- **上游**：源码分析、维护者和部署/发布契约。
- **下游**：保留、characterization 或独立删除 Issue。
- **测试接缝**：四类仓库内检查 + 延迟导入/动态加载专项检查 + 仓库外依赖人工确认。
- **模块角色 / 生命周期状态 / 负责人类别**：`policy` / `active` / HITL。审计是持续治理策略，本身不是待删除生产能力。

版本化审计记录位于 [`audits/issue-161-five-evidence.json`](./audits/issue-161-five-evidence.json)。`scripts/audit_module_usage.py` 对生产导入、动态注册、包级重导出和测试依赖执行 AST 扫描，包含函数体内延迟导入、`importlib` 动态加载和 `@tool` 定义级注册；记录中的仓库外依赖始终保留人工证据状态。扫描结果变化时必须重新评审记录，不能自动推导删除权限。

Base64 Tool 已在独立 Issue #377 的安全区清理中删除，结论记录在上述五证据审计文件；其余 `legacy/audit candidate` 的保留与删除继续依据逐对象审计和独立 Issue 决策。Web 单常量模块已在独立 Issue #168 完成删除。Issue #171 已消除重复日志桥安装状态：`web.llm_client.setup_agno_logging_bridge` 是唯一所有者，启动流程每次直接调用该幂等入口，不再保存外部门控状态。其余候选列表只要求审计，不授权删除、合并或重构。

旧 `agent/tools/confirmation_tool.py` 的四个 Agno `@tool` 从未挂载到任何 Agent，已随 #222（Phase 0 遗骸清理）连同其 characterization 测试一并删除。当前 Human-in-the-Loop 由 Planner 的类型化 `clarify` / `needs_confirmation` / `proposal` 决策、PlanExecutor 契约以及 Chainlit Action callback 共同拥有；不得以「补确认工具」名义重新引入 Agent 挂载式确认。

### 5.12 V2 持久化业务执行与确认续跑

- **职责**：从冻结的主数据、枚举映射附件和正式 Artifact 按固定白名单重建类型化 SessionState；复用既有 Application 执行，将成功候选、血缘、消息和 outbox 原子发布。内部业务状态不进入普通结果目录；Draft 不参与后续输入。
- **领域术语**：主数据、枚举映射附件、可引用会话产物、Task、Run、Artifact、Draft、字段映射、值映射、填充。
- **公共入口**：`BusinessApplication.postprocess`、`run_user_request`、`run_deterministic_plan` 的可选续跑参数、`ExecutionContinuation`、V2 Store/Worker；`private_business_logging` 提供请求级日志隐私作用域。
- **上游**：V2 自然语言消息、显式参数按钮、确认令牌及类型化 checkpoint。
- **确认边界**：瞬时失败耗尽有界自动恢复后，保存执行器实际计划、成功前缀、已用预算与 staging 会话；确认后跳过成功步骤，人工续跑再次失败终止。缺参数仍追问，不以确认补造参数。
- **清空边界**：明确清空命令复用 `is_explicit_clear_command` / `clear_session_data`，不调用 Planner；持久停用输入、作废当前业务引用和旧确认，受 fence 保护，保留历史本人内容与下载。
- **下游**：生产 Adapter 唯一组合、Contracts、只读标准字段与独立 V2 SQLite/Blob；Application 核心不依赖 V2 数据模型。
- **测试接缝**：两条跨轮完整链路、同名附件重填、配置根结构/Draft/导出兼容、成功步骤账本和已耗恢复预算、旧卡/哈希/主数据/lease/fence 失效、本人内容授权、普通会话安全能力投影和日志隔离。
- **模块角色 / 生命周期状态 / 负责人类别**：`public entrypoint / integration adapter / policy` / `active` / Application runtime + Web adapter。
- **物理所有者**：`v2/backend/toolwithagent_v2/runtime/` 与 `infrastructure/store.py`；共享续跑和隐私接缝位于 `application/`，业务领域变换继续由既有 Adapter 拥有。
- **静态分析盲区**：专业 Agent 延迟构造、可选 Adapter 注入和日志 ContextVar 作用域需要真实组合与异步/线程回归，不能以 Fake 执行器代替。
- **深度审查**：状态序列化与配置投影收口在 V2 纯函数模块，事务聚合仍由 Store 拥有；删除这些边界会把恢复与校验复杂性散到多个入口。Store 已超过软性行数预算，后续按事务聚合评估拆分，当前不为此引入通用仓储或新的领域实现。

## 6. 静态分析盲区

| 盲区 | 当前证据 | 维护规则 |
|---|---|---|
| 延迟导入 | 日志知识兼容门面在函数内部导入 `log_pattern_store`，正常分类路径不导入仓储 | caller count 为零时必须再做全文符号与运行路径检查 |
| 包级重导出 | `agent.tools`、Application adapters、规则生成包提供稳定门面，部分包使用 `__getattr__` 动态重导出 | 同时检查定义模块、`__all__`、`__getattr__` 与对象身份测试 |
| 动态加载 | FieldSkillAdapter 根据声明式注册表加载 Skills 脚本 | 同时检查注册表、脚本路径、函数名和生产组合 |
| 框架注册 | Chainlit callback 与 Agno tool 可通过装饰器进入生产路径 | 检查装饰器与框架入口，不以普通 Python caller 为唯一证据 |
| 仓库外依赖 | Python 模块可能被未纳入仓库的脚本、部署或用户导入 | 仓库内零引用只能记为仓库证据，必须由维护者确认仓库外依赖 |

## 7. 深度、软性预算与维护规则

- 行数只用于导航和评审触发。新增或深化后的单一模块接近 **400–500** 行时，应解释职责深度或提出拆分测试接缝；它**不作为 CI 硬门禁**，也**不作为质量评分**。
- 是否拆分同时考察模块接口、职责深度、耦合、变化率、局部性和测试接缝。小文件也可能是浅层模块。
- 一个模块只为一个调用者透传且删除后复杂性消失时，应重新评估其价值；删除后复杂性会分散到多个调用者时，应保留其杠杆。
- 新能力进入生产组合、公共入口迁移、生命周期改变或测试接缝改变时，必须在同一变更中更新本目录。
- 目录条目不得复制完整实现细节；调用者只需知道接口、不变量、错误模式、顺序和配置要求。
- 候选模块只能从 `audit-candidate` 进入独立 characterization 或删除 Issue，不得在相邻重构中顺手处置。
