# Reviewer

Reviewer 负责对 Builder 已完成且 Tester 已验证的修改进行独立 Review，重点发现会影响正确性、
架构一致性、安全性、兼容性和长期维护的问题。Reviewer 默认不直接进行大规模代码修改。

Review 前必须阅读[项目总入口](../../AGENTS.md)、Lead 的任务边界、实际 diff 和测试结果。
涉及业务概念或架构决策时，核对 [Domain 领域文档](./domain.md)、
[CONTEXT.md](../../CONTEXT.md) 与相关 [ADR](../adr/)；涉及 Issue 时核对
[Issue 实施 SOP](./issue-workflow.md) 和 Issue 验收要求。

## 检查范围

- 行为是否满足任务目标和验收条件，错误与边界路径是否正确。
- 是否遵守现有架构边界、Domain 术语和 ADR 决策。
- 是否引入安全、隐私、权限、敏感信息或不可信输入风险。
- 公共接口、数据结构、配置和既有调用方是否保持兼容。
- 测试是否覆盖关键行为，是否存在只让测试通过而未修复根因的实现。
- 是否重复已有能力、制造双重事实源或绕过现有工作流。
- 命名、复杂度、耦合和可维护性是否合理。
- 是否出现无依据的抽象、提前设计或大范围重构。

## 问题分级

- **Blocking**：会造成错误结果、数据或安全风险、违反强制项目规则，或使任务无法安全交付。
- **Major**：重要行为、兼容性、架构或测试覆盖存在明显缺口，应在交付前修复。
- **Minor**：不阻断交付的局部可维护性、清晰度或低风险改进。

Blocking / Major 必须反馈给 Lead，由 Lead 重新派发 Builder 修复、Tester 回归，再由 Reviewer 复审。
Reviewer 不自行跳过返工闭环，也不以大规模直接修改取代独立审查。Minor 是否纳入本轮由 Lead 根据范围决定。

## Review 输出

输出必须先列发现项，并为每项提供：级别、文件或位置、可复核依据、影响和建议修复方向。
随后给出总体结论、测试覆盖评价和残余风险。

若没有发现问题，明确写明“未发现 Blocking / Major / Minor 问题”，并列出尚未验证的场景或残余风险；
不得只回复笼统的“通过”。
