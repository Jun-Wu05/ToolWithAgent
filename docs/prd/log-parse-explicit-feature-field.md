# PRD：日志类型提取——显式指定分类特征字段

## 问题陈述

日志类型提取目前只能整体触发：用户说「日志类型提取」后，分类特征字段由系统自动探测（缺省 `log_type`）。当用户明确知道应该用哪个字段区分日志类型时（例如「把 category 字段作为日志类型」），系统无法接收这个意图——要么被忽略，要么被误解为枚举提取。更糟的是：如果 Planner 漏掉字段参数，系统会静默降级为自动探测，用户拿到一份按错误字段分类、但表面完全正常的结果（分类明细、入口/子规则、按钮、txt 全都在），错误继续流入下游字段映射与导出，几乎无法回溯。

## 解决方案

让「把 X 字段作为/当作/设为日志类型」类表达成为日志类型提取的显式分类特征字段入口：Planner 将其映射为携带 feature_field 的 log_parse 步骤；执行前校验该键确实存在于日志体键集合，不存在则停下追问并列出可用键；执行时显式值优先于自动探测，格式识别（JSON/KV）与日志体提取照常自动完成。产物与现有日志类型提取完全一致，另附未匹配行覆盖信息。一道 Planner 确定性后置守卫兜底：显式短语存在而步骤参数缺席时，宁可追问，绝不静默自动探测。

## 用户故事

US-1：作为规则配置操作者，我想在上传含原始日志的数据后说「把A字段作为日志类型」，以便系统按我指定的日志体键完成日志类型提取，得到与显式指令【日志类型提取】完全一致的结果（分类明细、入口/子规则、三按钮与 txt 导出）。

US-2：作为规则配置操作者，我想让「把A的枚举值作为日志类型」这类带「枚举」字样但含「作为日志类型」短语的表达同样按日志类型提取处理，以便我的自然说法不被误路由到枚举提取。

US-3：作为规则配置操作者，我想在指定的字段不存在于日志体键集合时收到追问（列出实际可用的字段名），以便快速纠正说法或字段名，而不是拿到静默的错误分类或一句干巴巴的报错。

US-4：作为规则配置操作者，我想让格式识别（JSON/KV）与日志体提取照常自动进行，以便我只指定分类字段、不必描述日志格式。

US-5：作为规则配置操作者，我想看到未归入任何类型的行数与样本（覆盖信息），以便判断日志中是否存在其他日志类型字段或脏数据，并决定是否换字段重跑。

US-6：作为规则配置操作者，我想让「提取A的枚举值，然后按A做日志类型分类」分解为两步并各自保留产物，以便枚举值列表可进后续值映射链路，同时拿到分类与规则。

US-7：作为规则配置操作者，我想让不带字段指定的「日志类型提取」「识别日志类型」维持自动探测行为完全不变，以便现有使用习惯与既有测试不受影响。

US-8：作为规则配置操作者，我想让 Planner 漏掉显式字段参数时被确定性守卫拦下追问，以便我的显式意图永远不会被无声忽略、换成自动探测的结果。

## 实现决策

### LogParseStep 显式分类特征字段

步骤契约新增可选字段 feature_field；不携带时一切行为与现状完全一致（自动探测路径不动）。feature_field 取值限于日志体键：JSON 字段名或 KV 键名，允许嵌套点分路径（如 `detail.event_type`）。

### Planner 操作语义与消歧

planner 提示词操作目录 log_parse 条目扩展：默认不选字段、由系统自动探测；仅当用户文本命中「把/将/拿 X 字段（的值）作为/当作/设为/当日志类型」「用 X 区分日志类型」「按 X 给日志分类」短语族时携带 feature_field。消歧规则改写原有「日志类型提取……不存在选择哪个字段」的绝对表述，并新增：带「枚举」字样但含「作为日志类型」短语的表达仍属 log_parse；「提取 X 的枚举值」无该短语时仍属枚举提取；复合句「提取 X 的枚举值，然后按 X 做日志类型分类」按数据依赖分解为枚举提取 + 日志类型提取两步，各自保留产物身份；无法判断时 Clarification。

### 显式意图确定性守卫

PlannerService 在模型输出 execute 后增加后置守卫（与既有威胁目标守卫同构）：用户文本命中规范短语族，而计划中不存在携带 feature_field 的 log_parse 步骤时，确定性改写为 clarification（reason_code 为 explicit_feature_field_ignored），提示确认要作为日志类型的字段。守卫只判短语族存在与参数缺席的矛盾组合，不从中文文本抽取字段名。

### 执行前键存在校验

PlanExecutor 执行前校验：步骤携带 feature_field 时，从会话原始日志行采样提取日志体键集合（KV 键名正则 + JSON 字段名，含嵌套点分路径）。精确命中放行执行；未命中返回 NEEDS_INPUT（reason_code 为 feature_field_not_found），追问文案列出实际可用键并对近似项标注提示；不代用户改参，不做大小写自动纠正。特征位于日志头的场景不支持显式指定，仍走自动探测。

### 适配器显式优先

日志解析适配器：步骤显式 feature_field 优先于格式识别的自动探测值；格式识别与日志体剥离照常自动执行（含既有 KV 纠偏）；显式携带时压制特征定位器（Step 2a）对特征字段的自动修正，强制走日志体路径提取。格式落到不支持的类型时沿用现有失败行为。

### 未匹配行覆盖信息

聚合阶段统计未包含分类特征字段的日志行，分类结果新增覆盖信息块（总行数、已匹配数、未匹配数、未匹配样本）；显式与自动两种模式共用同一统计。未匹配行不进入 classification_details，不参与入口/子规则生成与任何导出产物。渲染时在分类摘要下方单独展示未匹配行数与样本，并提示这些行可能属于其他日志类型字段（可指定其他字段或改用自动探测重跑）。

### 产物生命周期不变

结果仍写入现有日志分类会话槽位：成功整体覆盖旧分类，失败或 NEEDS_INPUT 不改变旧结果，主数据替换/清空时一并清除。不新增可引用会话产物类型，SessionFacts 不新增投影字段；本次使用的 feature_field 记录在分类结果自身的 feature_field 字段中，可审计。

## 测试决策

### 消息全链路 seam / 显式字段端到端

经用户消息入口驱动完整链路（Planner mock runner 产出携带 feature_field 的 log_parse，headless pipeline 三函数 mock）：断言指定键正确传入格式识别与分类、自动探测值被覆盖、分类结果写入会话、三按钮与产物渲染齐备；同时断言不携带 feature_field 时行为与现状一致。先例：现有 log_parse 单意图端到端测试。

### Planner 守卫 seam / explicit_feature_field_ignored

mock runner 返回裸 log_parse，配合真实守卫：用户文本含规范短语族时确定性改写 clarification；不含短语族时不干预；计划已携带 feature_field 时不干预；复合句缺后半步骤时同样拦截。先例：现有威胁目标守卫测试。

### 执行前键校验 seam / feature_field_not_found

以会话假件驱动执行前校验：键不存在时 NEEDS_INPUT 且文案包含可用键列表与近似提示；键存在（含点分路径）时放行；不携带 feature_field 的 log_parse 不做键校验，沿用现有日志存在校验。先例：现有执行器校验测试。

### 提示词语义 seam / 短语族与消歧条目

静态锁定 planner 提示词：log_parse 条目含显式分类特征字段语义；旧绝对表述「不存在选择哪个字段」已改写；消歧条目覆盖「枚举字样 + 作为日志类型」「复合句拆两步」「无法判断 Clarification」。先例：现有提示词语义测试。

### 语义评测 seam / 三类表达决策

语义评测集新增用例：「把A字段作为日志类型」「把A的枚举值作为日志类型」→ log_parse 携带 feature_field；「提取A的枚举值」→ enum_extract；复合句 → 两步计划。纳入既有评测流程与正确率口径。

### 聚合覆盖 seam / 未匹配行统计

真实聚合逻辑 + mock LLM：混合键集合的日志样本下，覆盖信息块的总数/匹配数/未匹配数/样本正确；未匹配行不出现在 classification_details 与生成的规则中；纯样本（全部行含键）时覆盖信息为全匹配。先例：真实样本回填测试（真实正则 + mock LLM）。

## 范围外

- 不修改 Excel 上传约束：主数据仍必须含「原始日志」列；「把某列作为日志类型」的列名指定不支持，出现时 Clarification 解释。
- 不支持日志头特征的显式指定（无稳定词法），仅自动探测。
- 不支持多字段组合作为分类特征字段。
- 不为日志分类结果新增可引用会话产物类型；多字段历史产物保留与回选由既有 Issue 跟踪。
- 不提供未匹配行的自动再分类或「未匹配桶」规则导出；仅展示覆盖信息，由用户决定换字段重跑。
- 「把A作为日志类型，再把B作为威胁类型」类复合意图（涉及字段映射指定语义）另行讨论，不在本 PRD。
- 不修改枚举提取的任何行为。

## 补充说明

- UI 模式：headless；不涉及页面、States 矩阵或设计稿。
- 术语「分类特征字段（Feature Field）」及消歧边界、覆盖信息规则已固化于 CONTEXT.md，本 PRD 与之保持同步；守卫短语族与 CONTEXT.md 消歧边界须同步维护。
- 全部决策沿用既有架构：独立 Planner 与 fail-closed（ADR-0005）、确定性后置守卫模式（威胁目标守卫先例）、会话产物生命周期（ADR-0006）；无新增难以逆转决策，因此无需新增 ADR。
