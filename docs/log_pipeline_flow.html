📌 用户操作

用户在 Chainlit 界面 上传 Excel (.xlsx)，或者直接粘贴日志文本。

  • Excel → file_handler.py 用 openpyxl 解析
  • 提取 原始日志 列作为 logs_str
  • 提取其它列为 simplified_data（用于后续字段映射/威胁填充）

📌 路由分发

chainlit_app.py 的 process_user_message() 负责判断用户意图：

用户输入 → RouterAgent → is_log_parser? → LogParserAgent

同时检测 is_mapping / is_threat / is_enum_extract 做多意图复用。

📌 上下文隔离

不同意图的 LLM 输入互不污染：

  • 日志解析：只传原始日志文本
  • 字段映射：拼接字段名列表
  • 威胁处理：只传文本，不拼字段数据

🔎 格式识别 — identify_log_format

agent/tools/pipeline/log_format_identifier.py

📌 输入 / 输出

logs_str (原始日志) → 采样 5 行 → Prompt 注入 → LLM → JSON { format, format_detail, delimiter, confidence, kv_connector, kv_separator, feature_position, feature_extract_regex }

📌 枚举归一化 已修复

LLM 返回的 format 字段经 normalize_log_format() 映射为枚举：

json / JSON / json格式→ JSON
kv / key=value / KV→ KV
space / 空格→ KV
semicolon / comma→ SEPARATOR
cef→ CEF
其它→ UNKNOWN

输出为大写（"JSON" 而非 "json"），这是后续 Step 2.5 需要特殊处理的地方。

📌 feature_position 三种模式

  • header_regex — 分类标识在日志头（如 "API SERVER"）
    → 输出 feature_extract_regex
  • kv_body — 分类标识在 body 的 KV 字段中（如 log_type=xxx）
  • positional — 固定列位置（如 CSV 第 N 列）

📌 Prompt 文件

agent/prompts/log_format_identify.md

要求 LLM 识别：JSON / KV / SEPARATOR / CEF / UNKNOWN
同时判定是否有日志头（header_regex）。

LLM 调用

📌 按 format_type 分流

json→ _try_extract_json_feature()
每行 JSON.parse 或"日志头+JSON"子串提取
kv / space / semicolon / comma→ _try_extract_kv_feature()
tokenize → 匹配 key=value / key:value
cef→ CEF 扩展解析

🚨 关键点位 最近修复

# L67 — CHANGED: 归一化小写，防御 Step1 输出 "JSON" 等大写值
format_type = (format_type or "").lower()

Step 1 的 normalize_log_format() 输出大写 "JSON"。
若不 lower()："JSON" != "json" → 走 else 分支 → KV 提取 → 误匹配 username 等字段 → 聚合值错误。

if feature_position == "header_regex":

    feature_value = m.group(1)

    # 回退到 JSON/KV body 提取

日志头有分类关键词时，header_regex 优先级最高，不依赖 format_type。

📌 5 个字段强制覆盖 关键防御

# log_format 用归一化枚举值强制覆盖 LLM 输出
parsed["log_format"] = _normalize_log_format(format_type)

# 其余用 setdefault（已有值不覆盖）
parsed.setdefault("log_format_detail", format_detail)
parsed.setdefault("feature_field", feature_field)
parsed.setdefault("feature_identifier", "")
parsed.setdefault("feature_count", value_count)
parsed.setdefault("classification_details", [])
parsed.setdefault("expert_summary", "")
parsed.setdefault("categorical_features", "")
parsed.setdefault("Diversion_method", "")
parsed.setdefault("fail_reason", "")
parsed.setdefault("total_lines", total_lines)
parsed.setdefault("matched_lines", matched_lines)

log_format 是唯一用 = 强覆盖的字段（其它用 setdefault 不覆盖 LLM 有效输出）。
原因：Prompt 要求枚举值但 LLM 仍可能输出自然语言，代码层兜底。

📌 _extra_values 过滤 防御

如果 LLM 在 classification_details 中新增了聚合统计里不存在的值（如按 username 分类）：

_extra_values = _existing_logtypes - _known_values
if _extra_values:
    logger.warning(f"LLM 新增无关分类值: {_extra_values}，已自动剔除")
    parsed["classification_details"] = [
        d for d in details if d["logtype"] in _known_values
    ]

📌 _missing_values 补漏 防御

如果 LLM 遗漏了低频分类（如 ssoaccess 占比 0.46%）：

_missing_values = _known_values - _existing_logtypes
if _missing_values:
    logger.warning(f"LLM 遗漏: {_missing_values}，自动补充")
    for _val in sorted(_missing_values):
        parsed["classification_details"].append({
            "logtype": _val,
            "matched_regex": "",
            "meaning": f"LLM 未分析（自动补充，出现 N 次）",
            "sample": aggregation_samples[_val]
        })

📌 _build_log_analysis 纯函数

互斥检测（优先级 CEF > JSON > KV > SEPARATOR）：

{
  "has_json_structure": bool,       # 互斥
  "has_cef_prefix": bool,           # 互斥
  "has_key_value_pairs": bool,      # 互斥
  "has_delimited_structure": bool,  # 互斥
  "delimit": ":" 或 "=",
  "tab": "," / ";" / "|" / "space"
}

注意 KV token 检测用 ^[a-zA-Z_]\w*= 排除时间戳和 IPv6 误判。

📌 _generate_feature_identifier Bug 1 修复

代码自动生成双捕获组正则（覆盖 LLM 输出），利用 header_end_marker 区分有头/无头日志：

# 有 header_end_marker（如 " - "）：
# Group1 只捕获 body（跳过 syslog 头部）
regex = rf'.*{escaped_marker}(.*{field}="([^"]+)".*)'

# 无 marker：
# Group1 = 整行（即 body）
regex = rf'(.*?{field}="([^"]+)".*)'

之前未区分有无头部，KV 正则 (.*?field="value".*) 的 Group1 总是捕获整行（含 syslog 头）。

📝 样例替换 — fill_sample_logs

agent/tools/pipeline/log_sample_filler.py

📌 定位

纯 Python 函数。 用 LLM 输出的 matched_regex 从原始日志中匹配真实样例行，替换 LLM 返回的占位符 sample。

📌 策略 A: 有 feature_identifier（双捕获组正则）

# fi_pattern 由 feature_identifier 编译而来
# feature_body_group / feature_value_group 决定哪个 group 提取什么
if fi_pattern and logtype:
    for line in lines:
        m = fi_pattern.search(line)
        if m.group(feature_value_group) == logtype:
            body_from_regex = m.group(feature_body_group)
            if body_from_regex != line:
                real_samples = body_from_regex   # Group1=body only
            else:
                real_samples = _strip_header(line, header_end_marker)  # fallback
            break

关键：当正则 Group1 捕获了完整行（等于 line），说明正则不够精确， 此时 fallback 到 _strip_header(line, header_end_marker) 剥离头部。

📌 策略 B: 无 feature_identifier → header_end_marker 剥离

# fi_pattern 为 None（feature_identifier 未生成或编译失败）
for line in lines:
    if logtype in line:  # 简单子串匹配
        real_samples = _strip_header(line, header_end_marker)
        break

📌 兜底

如果以上策略均匹配不到 → real_samples = "[匹配失败]"。

📌 参数自动提取 Bug 2 修复

# CHANGED: 从 classification dict 自动提取 feature_identifier
# 修复 chainlit_app.py 调用时未传 feature_identifier 导致 fi_pattern=None
if not feature_identifier:
    feature_identifier = classification.get("feature_identifier", "")

# header_end_marker 同理（已有逻辑）
if not header_end_marker:
    header_end_marker = classification.get("header_end_marker", "")

之前 chainlit_app.py 调用 fill_sample_logs(classification, logs_str) 只传了 2 个参数，feature_identifier 默认 ""， 导致 JSON 格式日志的 real_samples 输出了完整行（含 syslog 头）。
