## 二、现存核心问题及根因

### 2.1 威胁类型处理输出上一次结果

| 项目 | 内容 |
|------|------|
| **表现** | 用户输入"威胁类型处理"后，LLM 依然处理上一次的字段映射数据 |
| **根因** | `build_llm_input()` 无条件拼接 session 中的缓存数据，无论当前任务类型是什么 |
| **代码位置** | `web/input_builder.py` L20-23：`has_data = user_session.get("decoded_data") or user_session.get("decoded_fields")` |
| **严重程度** | 🔴 P0 — 核心功能阻断 |

**时序链：**

```
Step 1: 上传 Base64 → decoded_data/simplified_data 存入 session
Step 2: 用户输入"字段映射" → build_llm_input() 拼接缓存数据 → ✅ 正确
Step 3: 确认填充完成 → session 中 decoded_data 仍然存在
Step 4: 用户输入"威胁类型处理" → build_llm_input() 仍然拼接旧缓存数据 → ❌ 错误
```

**原因**：`build_llm_input()` **不检查用户当前请求意图**，只要 session 里有 `decoded_data` 或 `decoded_fields` 就优先拼接字段列表。LLM 看到字段列表后优先做字段映射，忽略用户的实际威胁类型处理请求。

### 2.2 Agno Route 模式导致的 5+ 分钟响应延迟

| 项目 | 内容 |
|------|------|
| **表现** | 一次字段映射请求耗时 453 秒（7.5 分钟） |
| **根因** | Agno TeamMode.route 模式下多次串行 LLM 调用 |
| **日志证据** | `[API] 开始调用 Team.run (尝试 1/3)，输入长度: 2187` → 453 秒后完成 |

**延迟拆解：**

```
一次字段映射请求 = 至少 3~4 次 LLM 调用串行执行：

RouterAgent: 判断路由方向 → 1次 LLM 调用（~60s）
FieldMappingAgent: 理解指令 + 读取标准字段表 → 1次 LLM 调用（~120s）
    → 调用 generate_mapping_table_tool（工具调用）
    → LLM 处理工具返回结果 → 再 1次 LLM 调用（~120s）
    → 输出 JSON 格式化 → 最终响应
总计: 3~4 次 × 每调用 1~2 分钟 = 5~8 分钟
```

**根本原因分析：**

1. Agno 对每个工具调用都产生一次额外的 LLM 调用（LLM 决定调工具 → 工具返回 → LLM 处理结果）
2. `field_weak.md` 提示词包含完整 654 行标准字段表，LLM 产生"需要全部记忆"的认知负担
3. `on_chat_start` 中的 `team.run("你好")` 预热操作额外消耗一次路由调用
4. 无超时保护机制

### 2.3 双层路由重复

| 路由层 | 位置 | 机制 |
|--------|------|------|
| Chainlit 硬路由 | `_route_request()` | 关键词匹配（威胁 > 枚举 > 映射） |
| Agno Team 路由 | `Team(mode=TeamMode.route)` | RouterAgent 语义路由 |

Chainlit 的关键词匹配先于 Agno Router，RouterAgent 形同虚设。

### 2.4 零 Agent 层测试

- 仅测试 Chainlit 的路由函数（`_route_request` 和 `_build_llm_input`）
- 无 Agent 推理结果正确性测试
- 无 Team 路由准确性测试
- 无工具函数调用测试

### 2.5 无结构化会话管理

- 50+ 个零散的 session key 字符串
- 无类型安全封装
- 键名拼写错误只能在运行时发现

## 三、优化方案

### 3.1 修复"威胁类型处理输出上一次结果"

**方案：上下文隔离 + 按需路由**

核心思想：**不要无条件拼接缓存数据，让 RouterAgent 拥有完整的会话视图，由它自己判断需要什么。**

```python
# 在 handle_user_message() 中
user_lower = user_text.lower()

# 1. 检测意图
is_threat = any(kw in user_lower for kw in THREAT_KEYWORDS)
is_enum = any(kw in user_lower for kw in ENUM_KEYWORDS)
is_mapping = any(kw in user_lower for kw in MAPPING_KEYWORDS)

# 2. 按意图构建 LLM 输入
if is_threat:
    # 威胁路由：只传用户文本，不拼接字段数据
    full_input = user_text
elif is_enum:
    # 枚举路由：提示用户上传 Excel
    await cl.Message(content="📋 请上传枚举映射表...").send()
    return
elif is_mapping or user_session.get("decoded_data"):
    # 映射路由：拼接字段数据
    full_input = build_llm_input(user_text, user_session)
else:
    # 其他：让 RouterAgent 自己判断
    full_input = user_text
```

**关键设计原则：**

| 原则 | 实现 | 效果 |
|------|------|------|
| 上下文隔离 | 映射路由才拼接字段数据，威胁路由只传文本 | 不互相干扰 |
| 状态闭环 | 每个任务完成后释放关联 session key | 不残留旧状态 |
| 按需构建 | 每种路由只构建自己需要的上下文 | 减少 LLM 认知负担 |

### 3.2 性能优化（5分钟 → 30秒）

**方案 A（推荐）：去掉 Agno 框架，直接调用 LLM API**

```
当前: 用户 → Chainlit → Team.run → RouterAgent(LLM调用×1) → MemberAgent(LLM调用×2) → Tool(LLM×1)
优化后: 用户 → Chainlit → build_prompt() → API一次调用 → parse() → 返回
```

估算时间：1 次 LLM 调用 × 30~60 秒 = **30~60 秒**

**方案 B（保留 Agno 框架）：逐步优化**

| 优化项 | 预估效益 | 难度 |
|-------|---------|------|
| 去掉 `team.run("你好")` 预热 | 节省 1 次调用（~60s） | 低 |
| 关键词预筛跳过 RouterAgent | 节省 1 次调用（~60s） | 低 |
| 优化 prompt：声明"参考字典" | 减少 LLM 认知负担（~30s） | 低 |
| 加 120s 超时保护 | 避免卡死 | 低 |

**为什么不推荐保留 Agno？**

- 当前工具（`field_mapping_tool` 用编辑距离算法匹配字段、`threat_type_tool` 用规则匹配）**都不需要 LLM 调用**，纯 Python 就能完成
- LLM 只需要做一次决策（"这些字段应该映射为什么"）就足够了
- Agno 框架对每个工具调用都产生一次额外的 LLM 调用

- 将 `reference/gui/` 目录完全删除
- 确认 `agent/shared/` 稳定运行后清理冗余文件

```xml
    <item>标准字段表（仅使用"系统属性名称"列）</item>
  </input>

    <constraint>只使用输入的原始字段，不多不少</constraint>
    <constraint>只能输出标准字段表中的中文系统属性名称，否则输出"未匹配"</constraint>
    <constraint>严禁自造字段、严禁翻译、严禁输出英文</constraint>
    <constraint>严禁从日志样本中提取新字段</constraint>

    <rule key="tls_, ja3, cert" value="tls协议" />
    <rule key="dns_, query, rcode" value="dns协议" />

    <rule key="无明显特征" value="按 事件→威胁→流量→主机→设备 检索" />
  </object_mapping>

    <rule key="src, source, from" value="源地址类（优先匹配 http协议 对象）" />
    <rule key="dst, dest, target" value="目的地址类" />
    <rule key="time, timestamp, date" value="时间类" />

    <rule key="type, category" value="类型类（按对象匹配）" />
    <rule key="id, uuid, code" value="标识类" />

    <rule key="risk" value="威胁等级" />
    <rule key="status, result" value="状态/结果类" />

    <rule key="count, num, size, bytes" value="计数/大小类" />

    <rule>仅允许1级邻近对象回退</rule>

  <matching_strategy>
    <rule>优先：对象一致 + 语义一致 + 标准字段描述一致</rule>
    <rule>字段为空 / 样本不足 → 允许弱匹配</rule>
    <rule>当标准字段表中没有任何字段与原始字段语义匹配时，必须输出"未匹配"，严禁创造新字段名</rule>

    <rule>仅允许1级邻近对象回退</rule>
  </matching_strategy>

    <example>

    ]
    </example>
    <rule>只输出JSON，不输出任何解释、思考、备注</rule>
    <rule>输出前自查：每个"系统属性名称"的值必须来自标准字段表的中文列，如果值是英文说明选错了列，必须修正后再输出</rule>
  </output_format>
</prompt>
```

**注意事项：**
- 不使用模型不认识的标签名 → 用 `<rule>`, `<task>`, `<output>`
- 避免深层嵌套（最多 3 层）
- 关键约束放最后（LLM 对结尾内容记忆最强）
- 保留所有规则，先完整等价转换再逐步精简
- XML 内容中的 `"` 会被 prompt 注入框架转义，无需额外处理

### 3.5 流畅 Agent 交互设计

当前"无边界"的交互模式导致 LLM 被旧数据误导。重构后的交互流程：

```
用户输入
  │
  ├─ 检测意图（关键词匹配）
  │   ├─ 威胁 → 只传用户文本，放入 THREAT_CONTEXT
  │   ├─ 映射 → 拼接字段数据，放入 MAPPING_CONTEXT
  │   ├─ 枚举 → 提示上传 Excel 文件
  │   └─ 其他 → 转交 RouterAgent
  │
  ├─ 按路由构建上下文（过滤无关 session 数据）
  │
  ├─ 调用 LLM（单次调用，非多层路由）
  │
  └─ 操作完成后释放关联 session key
```

**边界确认设计：**

| 机制 | 实现方式 | 效果 |
|-----|---------|------|
| 任务类型检测 | 前端关键词匹配 + 意图识别 | 区分"映射""威胁""枚举" |
| 上下文隔离 | 每种任务只构建自己需要的上下文 | 互不污染 |
| 状态闭环 | 每个任务完成后释放关联 session key | 不残留 |
| 用户确认 | 用户切换任务时主动告知 | UX 透明 |
