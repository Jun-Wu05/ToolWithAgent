# V2 产品成熟度评估（2026-11-26）

> 基线：codex/v2-development @ bea3ec50（#466 三层分工契约合并后）。
> 作用：定义前端体验批次（「V2 前端问题清单」16 条 + 场景走查新增项 W0）的**完成定义**，并给出跨过「内部工具」档所需的下一阶段输入。
> 状态：评估快照。交互维度分数以原型对照（3 变体 × 5 状态）与同类产品一手研究结论为准，可能修正。

> 成熟度五级刻度（本文件所用）：L1 演示可用 → L2 能用但处处硌手 → L3 内部可日常使用 → L4 敢托付（有质量评测与回归门禁）→ L5 可对外运营（有运维、多人、开放性）。

## 结论

本批工作项全部完成后：**L3 边缘（内部可日常使用），100 分制约 60–65 分**，较当前「L2、45 分上下」上升一个档位。

本批的本质是把「能用」补成「会用」：消摩擦、立引导、控密度。完成后，新用户第一次独立跑通「上传 → 日志类型提取 → 标准字段映射 → 填充 → 导出」的成功率，从「要人带」变为「自己能」。但产品成熟度上限由未修部分决定：不解决下文三道坎，只能停在「内部好工具」，跨不到「敢托付的产品」。

## 封顶在「内部工具」的三道坎（均不在本批范围）

1. **质量评测基线（最关键）**。产品对用户的核心承诺是「结果可信」：映射对了没有、填充值对了没有，目前没有任何可度量的答案。交互再顺，只是把用户更快地送到一个 unverifiable 的结果面前。建议下一阶段独立立项：评测集、准确率指标、报告。
2. **真浏览器回归门禁**。本批工作项全部动前端，回归保障却仍依赖会话内临时脚本（#459 的验收信号即依赖真浏览器）。playwright 进 devDependencies 与 CI 门禁的评估，应在本批过程中完成，而非批后补。
3. **运维与多人故事**。部署形态、数据备份、真实账户体系。只要还是「一台机器一个 SQLite」，成熟度标签只能是 internal。建议入 DISCUSSIONS 排队待议。

### 交互不变量（原型对照的评判标准）

1. **空状态必须教会，不只列出**——模板要么可直发（无占位符），要么点入有样例、说明期望的文件形态；
2. **每个终态卡恰有一个主操作**——次要操作收进固定区或右侧工作区；chips 与卡片按钮不得重复同一动作（#465 原则推广到分类结果卡）；
3. **有前置条件的路径不隐身**——填充需要枚举映射附件，这件事在用户「想填充」的时刻必须以引导出现，而不是静默无入口；
4. **进行中的叙事发生在对话流内**，不是输入框上方的横条；
5. **失败就近恢复**——失败消息出现在哪个上下文，重试入口就在哪里。
