# 复合意图分解技能

## 何时使用
当用户的**一条消息**里包含 **2 个及以上不同操作意图**，且这些操作之间存在**先后依赖关系**（A 的结果是 B 的输入）。典型场景：

- "把这些枚举值进行威胁类型映射" → 枚举值（已有）+ 威胁映射 + （隐含）使用枚举值作为映射输入
- "把这些枚举值做威胁映射然后填充回子规则里" → 威胁映射 + 填充
- "提取 ruleCategoryName 的枚举值，下载 Excel 填好后再填充" → 枚举提取 + 导出 + 填充
- "做字段映射，然后提取某字段枚举值" → 字段映射 + 枚举提取

**不使用本技能的情况**（这些是单意图或冲突消歧，走正常路由）：
- 单一操作："做威胁映射"、"提取枚举值"、"字段映射"
- 二选一冲突："威胁类型字段映射"（字段映射 OR 威胁映射，需澄清）

## 操作步骤

### Step 1: 识别复合意图
分析用户消息，判断是否包含多个有依赖关系的操作。依赖关系的标志：
- 出现"然后"、"再"、"接着"、"之后"等顺序词
- 后一个操作的输入依赖前一个操作的输出（如"填充"依赖"映射"的结果）
- 多个动作动词指向不同目标

### Step 2: 分解成有序步骤
将复合请求分解成有序步骤列表，每步对应一个原子操作。步骤类型必须是以下之一（系统据此调用对应执行器）：
- `log_parser` — 日志类型识别/格式识别
- `mapping` — 标准字段映射
- `enum` — 枚举值提取
- `threat` — 威胁类型映射
- `fill` — 填充到子规则/配置

参考 `references/step-types.md` 了解每种步骤类型的数据依赖和执行细节。

### Step 3: 输出计划标记
在回复中输出计划标记，格式严格如下（系统会解析此标记并自动执行）：

```
[PLAN:步骤1类型|步骤2类型|...]
```

**重要**：
- 标记必须独占一行
- 步骤类型用 `|` 分隔
- 顺序即执行顺序
- 输出标记后，**可以**附带简短说明（如"我将先执行威胁映射，再自动填充"），但标记是系统执行的唯一依据
- **不要**自己执行这些步骤，系统会自动按序执行

### Step 4: 数据传递说明
系统会保留用户原始消息全文，并在每步执行时传递给对应执行器。因此：
- 不需要在标记里重复数据
- 步骤间的结构化数据（如枚举值、映射结果）由系统在 session 中自动传递
- 例如：威胁映射步骤会自动读取上一步提取的枚举值

## 输出格式

### 示例 1：威胁映射 + 填充
用户输入："把这些枚举值都进行威胁类型映射，然后填充回子规则里"

输出：
```
我将把这个请求分解为两步：先做威胁类型映射，再自动填充到子规则。

[PLAN:threat|fill]
```

### 示例 2：枚举提取 + 导出 + 填充
用户输入："提取 ruleCategoryName 的枚举值，下载 Excel 填好后再填充"

输出：
```
这个请求包含三步：先提取枚举值，导出映射表，最后填充。

[PLAN:enum|fill]
```
（注：导出 Excel 由用户在本地完成，不作为自动步骤）

### 示例 3：字段映射 + 枚举提取
用户输入："先做字段映射，然后提取 severity 字段的枚举值"

输出：
```
我将先执行字段映射，再提取枚举值。

[PLAN:mapping|enum]
```

## 约束与边界

- **只分解，不执行**：本技能只输出 [PLAN] 标记，实际执行由系统自动完成
- **步骤类型有限**：只能是 log_parser / mapping / enum / threat / fill 五种，不要自创
- **保留原始语义**：分解时不要改变用户的原始意图，只是拆分成可独立执行的步骤
- **单意图不分解**：如果用户只表达一个操作，不要使用本技能，走正常路由
- **冲突不分解**：如果是"二选一"的冲突（如"威胁类型字段映射"），不要分解，走消歧逻辑（询问用户）
- **填充步骤需有前置数据**：fill 步骤前必须有产生映射数据的步骤（threat/enum），否则系统会提示无数据
