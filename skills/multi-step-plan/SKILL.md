# 复合意图分解技能【已废弃，仅存档】

> **状态：已被取代。** 复合意图分解现由 PlannerAgent（agent/core/planner.py，提示词
> agent/prompts/planner.md）+ PlanExecutor + web/adapters/ 的类型化计划架构实现
> （ADR-0005）。本文档描述的 `[PLAN:...]` 标记机制已从代码中移除，本技能不被加载。
> 保留本文档仅作为设计演进的历史记录；新增编排能力请扩展 StepSpec 步骤类型，
> 参见 ADR-0008（字段调整技能的类型化接线）。


## 何时使用
当用户的**一条消息**里包含 **2 个及以上不同操作意图**，且这些操作之间存在**先后依赖关系**（A 的结果是 B 的输入）。典型场景：

- "把这些枚举值进行威胁类型映射" → 枚举值（已有）+ 威胁映射 + （隐含）使用枚举值作为映射输入
- "把这些枚举值做威胁映射然后填充回子规则里" → 威胁映射 + 填充
- "提取 ruleCategoryName 的枚举值，下载 Excel 填好后再填充" → 枚举提取 + 导出 + 填充
- "做字段映射，然后提取某字段枚举值" → 字段映射 + 枚举提取

**不使用本技能的情况**（这些是单意图或冲突消歧，走正常路由）：
- 单一操作："做威胁映射"、"提取枚举值"、"字段映射"
- 二选一冲突："威胁类型字段映射"（字段映射 OR 威胁映射，需澄清）

## 核心原则：步骤指令自包含（ADR-0004）

分解出的每个步骤，必须携带执行所需的全部参数。**你的职责不是分类，而是 Synthesis（综合判断）**——你要读懂用户意图、结合会话状态和字段列表，提取出每步需要的具体参数（如字段名、目标位置），写进计划标记里。

执行器（handler）不会从用户原文猜测参数，它们只接收你在计划中提供的显式参数。如果你没有提取出参数，执行器就无法正确执行。

## 操作步骤

### Step 1: 识别复合意图 + Synthesis
分析用户消息，判断是否包含多个有依赖关系的操作。依赖关系的标志：
- 出现"然后"、"再"、"接着"、"之后"等顺序词
- 后一个操作的输入依赖前一个操作的输出（如"填充"依赖"映射"的结果）
- 多个动作动词指向不同目标

**同时做 Synthesis**：结合当前会话状态（已上传文件、字段列表、已有映射结果）和用户原文，判断每步需要的具体参数。

### Step 2: 分解成有序步骤 + 提取参数
将复合请求分解成有序步骤列表，每步对应一个原子操作。步骤类型必须是以下之一：
- `log_parser` — 日志类型识别/格式识别
- `mapping` — 标准字段映射
- `enum` — 枚举值提取
- `threat` — 威胁类型映射
- `fill` — 填充到子规则/配置

**每步提取参数**（参考 `references/step-types.md` 的 params 定义）：

| 步骤类型 | 需提取的 params | 来源 |
|---------|----------------|------|
| `enum` | `field`（要提取枚举值的字段名） | 用户原文 + 字段列表 |
| `fill` | `field`（回填目标字段名）、`source`（数据来源：threat/enum） | 对话上下文 + 字段列表 |
| `threat` | 通常无 params（数据来自 data_deps） | — |
| `mapping` | 通常无 params | — |
| `log_parser` | 无 params | — |

**声明数据依赖**：如果某步需要前序步骤的产出，用 `data_deps` 声明（值为前序步骤的 type）。

### Step 3: 输出 JSON 计划标记
在回复中输出计划标记，格式严格如下（系统会解析此标记并自动执行）：

```
[PLAN:{"steps":[{"type":"步骤类型","params":{...},"data_deps":[...]}]}]
```

**格式要求**：
- 标记是 `[PLAN:` 开头、`]]` 结尾的 JSON 对象
- `steps` 数组，每个元素至少含 `type`
- `params` 和 `data_deps` 可选（无参数时可省略）
- 输出标记后，**可以**附带简短说明（如"我将先执行威胁映射，再自动填充"）
- **不要**自己执行这些步骤，系统会自动按序执行

## 输出格式示例

### 示例 1：枚举提取 + 威胁映射 + 填充（完整三步）
用户输入："把漏洞名称的枚举值提取出来后，进行威胁类型映射填回去"

会话状态：已上传日志，字段列表含"漏洞名称"，已有 mapped_sub_rules。

输出：
```
我将把这个请求分解为三步：先提取漏洞名称的枚举值，再做威胁映射，最后填充回子规则。

[PLAN:{"steps":[{"type":"enum","params":{"field":"漏洞名称"}},{"type":"threat","data_deps":["enum"]},{"type":"fill","params":{"field":"漏洞名称","source":"threat"},"data_deps":["threat"]}]}]
```

### 示例 2：威胁映射 + 填充（枚举值已存在）
用户输入："把这些枚举值都进行威胁类型映射，然后填充回 alarm_category 里"

输出：
```
我将先做威胁类型映射，再填充到 alarm_category 字段。

[PLAN:{"steps":[{"type":"threat"},{"type":"fill","params":{"field":"alarm_category","source":"threat"},"data_deps":["threat"]}]}]
```

### 示例 3：字段映射 + 枚举提取
用户输入："先做字段映射，然后提取 severity 字段的枚举值"

输出：
```
我将先执行字段映射，再提取 severity 字段的枚举值。

[PLAN:{"steps":[{"type":"mapping"},{"type":"enum","params":{"field":"severity"},"data_deps":["mapping"]}]}]
```

## Synthesis 要点

**你必须自己理解上下文，提取参数，不要把理解工作推给执行器。**

- 用户说"提取漏洞名称的枚举值" → 你要在 params 里写 `"field":"漏洞名称"`，而不是让执行器自己猜
- 用户说"填回去" → 你要结合字段列表判断填回哪个字段，在 params 里写 `"field":"漏洞名称"`（或对应的目标字段名），而不是让执行器从原文抠
- 字段列表在会话上下文的"可用数据字段列表"中，你可以直接引用其中的字段名

**禁止的反模式**（等同于把理解外包给执行器）：
- 只输出步骤类型不提取参数：`{"type":"fill"}`（field 从哪来？）
- 含糊引用：`{"type":"fill","params":{"field":"用户说的那个字段"}}`（执行器不会理解）

## 约束与边界

- **只分解 + 提取参数，不执行**：本技能只输出 [PLAN] 标记，实际执行由系统自动完成
- **步骤类型有限**：只能是 log_parser / mapping / enum / threat / fill 五种，不要自创
- **保留原始语义**：分解时不要改变用户的原始意图，只是拆分成可独立执行的步骤
- **单意图不分解**：如果用户只表达一个操作，不要使用本技能，走正常路由
- **冲突不分解**：如果是"二选一"的冲突（如"威胁类型字段映射"），不要分解，走消歧逻辑（询问用户）
- **填充步骤需有前置数据**：fill 步骤前必须有产生映射数据的步骤（threat/enum），且要声明 `data_deps`
- **提取不到参数时**：如果上下文信息不足以确定某步的参数（如用户没说填到哪、字段列表也没有线索），不要瞎编——省略该 params 字段，系统校验层会追问用户
